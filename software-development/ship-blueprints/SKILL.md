# Ship Blueprints — Generation, Data Truth, Deploy

Blueprints are static SVGs at `public/ship-blueprints/{slug}.svg`, one per
ship (856/856, all statuses), generated by
`scripts/generate-ship-blueprints.py`. They replace the deleted
`coming-soon.png` placeholder everywhere ship imagery renders.

## Regenerate
    cd <project-root>
    python3 scripts/generate-ship-blueprints.py
Reads STAGING_DATABASE_URL from CLAUDE.local.md (never echo it). Writes all
856 SVGs. Re-run after any ship geometry/class data correction.

## Derivation hierarchy (per ship)
1. verified DB geometry (lengthMeters/beamMeters sane)
2. lengthFeet -> meters — takes PRECEDENCE over beam*ratio when feet exist
3. beam from GT^(1/3)
4. class -> typical L/B from known-class averages
5. vesselType defaults (last-resort floor; gives an honest EST sheet)
Approximated values print "(EST)" on the sheet — keep that honest.

## Data-truth pitfalls (2026-09 campaign)
- Corrupt lengthMeters exist (icon-of-the-seas 27.4 m; carnival-celebration
  35 m; both had good lengthFeet). After ANY generator change, grep
  icon-of-the-seas.svg for 'LOA 364.5 M'. A beam*ratio override regression
  reached LIVE staging and was caught only by VISION review of a screenshot
  — DOM assertions cannot see scale/text errors.
- 14 ships' shipClass were corrupted by the scraper appending the 'Speed'
  field label ('River CruiserSpeed'). Fixed at source:
      UPDATE ships SET "shipClass" = regexp_replace("shipClass", 'Speed$', '')
      WHERE "shipClass" ~* 'speed$';   -- 14 rows, staging + prod
  If a sheet's gold class line ends '...SPEED', fix data, not template.
- Ships.detail payload shape changes REQUIRE bumping the Redis cache key
  (`ship:v2:${slug}` in detail.ts + all admin.ts invalidations) — payloads
  cache 1h and survive deploys; old-shape entries hide new fields.

## Hero toggle rule
ShipImageToggle renders a toggle ONLY when a real photo exists
(`hasPhoto = !!storedImage || !!heroImage`, computed server-side; the
BYTEA storedImage row must be destructured out of the spread — never
serialize it). Blueprint-only heroes show the sheet directly with NO Photo
button. Parents hide the photo gradient/title overlay while the blueprint
is shown (onViewChange) or the sheet gets a doubled title.

## Debugging a 'button/widget is missing' report
When the user says the toggle is missing but your Playwright suite says PASS,
the defect is in the TEST'S COVERAGE, not the code. Before theorizing:
1. ASK which URL/component they're looking at. Do not guess.
2. Enumerate the surfaces that own the widget — detail hero, cards, modals —
   and check each. A widget wired into ONE surface is a missing feature
   elsewhere, not a bug.
3. Never invent a route. Confirm the path exists in app/ before building a
   theory on it (a 200 on a marketing catch-all is not a real page).
4. Don't do bundle archaeology (grepping _next chunks, buildId, webpack.js)
   to answer 'is it visible' — fetch the page and enumerate the DOM.
Real case 2026-09-05: toggle existed only on the detail hero; user was on
/app/ships (browse grid) where cards had none. One clarifying question found
it after ~20 wasted tool calls.

## Deploy
Commit develop -> merge staging -> push (Railway auto-deploys ~5-8 min).
A 200 on /api/health can still be the OLD build — verify asset CONTENT:
    curl -s https://cruise-intelligence-staging.up.railway.app/ship-blueprints/<slug>.svg | grep 'LOA'
Production promotion (staging -> main) requires explicit user approval.
Local dev DB has 0 ships — verify UI on staging via Playwright (e2e-dm
account; free tier is gated to /pricing; sign-in route is /login).
